# Аудит проекта Medical Booking Service

Дата: 2026-03-07

Проверено:
- структура монорепозитория, конфиги, Docker Compose, Dockerfile, CI/CD
- ручной аудит `bronivik_jr` и `bronivik_crm`
- `go test ./...` для обоих модулей
- `go vet ./...` для обоих модулей
- `go test -race ./...` для обоих модулей

Ограничения проверки:
- `golangci-lint` локально не установлен
- `govulncheck` завершился внутренней ошибкой тулчейна, поэтому внешняя база Go-уязвимостей не была полноценно провалидирована

## Краткий вывод

Проект в целом выглядит рабочим на SQLite и покрыт тестами лучше среднего, но в текущем состоянии у него есть несколько серьёзных проблем:

1. Межсервисное бронирование оборудования между `bronivik_crm` и `bronivik_jr` может приводить к двойным бронированиям.
2. В `bronivik_crm` сломана поддержка длительностей больше одного слота, хотя UI их предлагает.
3. Режим `worker` в `bronivik_jr` запускает лишние сервисы и дублирует фоновые задачи.
4. Заявленная поддержка PostgreSQL неполная и в нескольких местах небезопасна.
5. Конфиги, `.env.example`, `docker-compose.yml` и реальный код заметно разошлись.

Ниже список findings по приоритету.

## Critical / High

### 1. Внешние бронирования оборудования могут обходить уже существующие заявки и приводить к переполнению слотов

Где:
- `bronivik_jr/internal/database/items_api.go:41-80`
- `bronivik_jr/internal/database/bookings.go:27-34`
- `bronivik_jr/internal/models/constants.go:3-8`

Проблема:
- `CreateExternalBooking()` считает занятыми только записи со статусом `"approved"`.
- Внутренняя логика `bronivik_jr` использует статусы `pending/confirmed/canceled/changed/completed`.
- `GetBookedCount()` считает занятыми почти все статусы, кроме `canceled/rejected`, а `CreateExternalBooking()` нет.

Следствие:
- если оборудование уже занято обычной заявкой `pending` или `confirmed`, CRM всё равно может создать внешнее бронирование;
- статусная модель между внутренними и внешними заявками фактически расходится.

Что сделать:
- унифицировать статусы между сервисами;
- при расчёте доступности использовать один общий путь, а не отдельный SQL с `"approved"`;
- добавить интеграционный тест: `pending/confirmed` в `bronivik_jr` должны блокировать внешнюю бронь из `bronivik_crm`.

### 2. В `bronivik_crm` UI разрешает 60/90/120+ минут, но БД принимает только ровно один слот

Где:
- `bronivik_crm/internal/bot/bot.go:450-503`
- `bronivik_crm/internal/db/database.go:1105-1119`
- `bronivik_crm/internal/db/database.go:1255-1267`

Проблема:
- UI предлагает длительности `30, 60, 90, 120, 150, 180` минут.
- При финальном сохранении `validateSlotAlignmentTx()` требует, чтобы `end-start == slotDuration`, то есть строго один слот.

Следствие:
- пользователь проходит сценарий до подтверждения, но бронь на 60+ минут падает на последнем шаге;
- фича "несколько подряд слотов" фактически не работает.

Что сделать:
- либо разрешить диапазон `n * slotDuration`, если все слоты подряд свободны;
- либо убрать длинные длительности из UI;
- добавить тест на успешное создание брони на 60/90/120 минут.

### 3. `bronivik_jr` в режиме `worker` поднимает не только напоминания, но и API, backup loop и Sheets worker

Где:
- `bronivik_jr/cmd/bot/main.go:38-118`
- `bronivik_jr/cmd/bot/main.go:280-290`
- `docker-compose.yml:91-122`

Проблема:
- флаг `workerMode` вычисляется в начале, но почти вся инициализация выполняется до ветки `if workerMode`.
- Контейнер `bronivik-jr-worker` запускает `./bot worker --job=reminders`, но реально поднимает:
  - `SheetsWorker`
  - HTTP API
  - backup service
  - reminder loop

Следствие:
- несколько контейнеров одновременно выполняют фоновые задачи на одной SQLite БД;
- можно получить дублирование sync-задач, резервных копий и лишнюю конкуренцию за файл БД;
- поведение контейнера не соответствует названию и Docker Compose.

Что сделать:
- рано разделить `bot mode` и `worker mode`;
- в worker-процессе оставлять только нужный job;
- добавить явный `switch` по подкомандам.

### 4. Поддержка PostgreSQL заявлена, но частично сломана

Где:
- `bronivik_jr/internal/database/database.go:308-423`
- `bronivik_jr/internal/database/database.go:438-456`
- `bronivik_jr/internal/database/items_api.go:68-80`
- `bronivik_crm/internal/db/database.go:682-710`

Проблема:
- в `bronivik_jr` миграции для legacy-колонок используют SQLite-ориентированные типы и дефолты (`BOOLEAN ... DEFAULT 0`, `INTEGER`), а ошибки проглатываются;
- в `bronivik_crm` `ensureHourlyBookingColumns()` делает то же самое;
- внешняя бронь в `bronivik_jr` вставляет `user_id = 0`, хотя в PostgreSQL `bookings.user_id` связан FK с `users(telegram_id)`.

Следствие:
- схема на PostgreSQL может остаться частично несовместимой;
- часть колонок может не добавиться, но приложение продолжит запуск;
- внешние бронирования через API могут падать на FK.

Что сделать:
- разделить миграции SQLite/PostgreSQL полностью;
- не глотать schema drift для PostgreSQL;
- для внешних заявок либо убрать FK на `user_id`, либо хранить отдельный тип владельца, либо создавать технического пользователя.

### 5. Проверка доступности слотов в `bronivik_crm` игнорирует обеденный перерыв, хотя конфиг и схема его поддерживают

Где:
- `bronivik_crm/internal/db/database.go:1180-1233`
- `bronivik_crm/configs/cabinets.yaml`
- для сравнения: `bronivik_crm/internal/slots/generator.go:71-107`

Проблема:
- активный код расчёта расписания (`resolveScheduleWindowTx` + `checkSlotAvailabilityTx`) учитывает только начало/конец рабочего окна;
- поля `lunch_start/lunch_end` читаются в схему и конфиг, но в runtime-логике фактически не используются;
- при этом рядом лежит альтернативный `slots/generator.go`, где обеденный перерыв уже реализован, но он не задействован.

Следствие:
- система может предлагать и сохранять записи во время обеда;
- есть явный дрейф логики между двумя реализациями слотов.

Что сделать:
- оставить один источник истины для расчёта слотов;
- встроить lunch/override в текущий DB-path;
- добавить тесты на блокировку обеденного интервала.

## Medium

### 6. gRPC availability API кэширует список аппаратов один раз при старте и не видит обновления

Где:
- `bronivik_jr/internal/api/handlers.go:16-33`
- `bronivik_jr/internal/api/handlers.go:47-50`
- `bronivik_jr/internal/database/items.go:196-214`

Проблема:
- `AvailabilityService` строит `itemsByName` только в `NewAvailabilityService()`.
- После добавления/переименования/деактивации аппаратов HTTP API работает с актуальным `db`, а gRPC остаётся на старом снимке.

Следствие:
- часть клиентов будет видеть разные данные в HTTP и gRPC;
- новые аппараты не появятся в `GetAvailability`, пока сервер не будет перезапущен.

Что сделать:
- убрать локальный snapshot и ходить в `db` на каждый запрос;
- либо подписать сервис на refresh кэша.

### 7. Auth-конфиг `bronivik_jr` нельзя реально выключить, а health endpoints проходят через auth middleware

Где:
- `bronivik_jr/internal/config/config.go:242-255`
- `bronivik_jr/internal/api/http_server.go:61-65`
- `bronivik_jr/internal/api/http_server.go:331-347`
- `docker-compose.yml:83-84`

Проблема:
- `applyDefaults()` принудительно включает `API.Auth.Enabled = true`, если в YAML выставлено `false`;
- `/healthz` и `/readyz` завернуты тем же middleware, что и боевые API;
- docker healthcheck использует захардкоженные `key1/extra1`.

Следствие:
- нельзя корректно отключить auth в конфиге;
- healthcheck ломается, если реальные ключи отличаются;
- поведение трудно предсказать при деплое и интеграции с внешним оркестратором.

Что сделать:
- различать "не задано" и "задано false";
- вывести health/readiness из auth middleware;
- убрать hardcoded ключи из Docker healthcheck.

### 8. Конфиги, `.env.example` и Docker Compose расходятся по именам и смыслу переменных

Где:
- `.env.example:13-21`
- `bronivik_jr/configs/config.yaml:61-64`
- `bronivik_jr/configs/config.yaml:86-95`
- `docker-compose.yml:54-66`
- `docker-compose.yml:146-152`
- `bronivik_crm/configs/config.yaml:33-38`

Проблема:
- root `.env.example` рекламирует `API_AUTH_KEYS` и `GOOGLE_SPREADSHEET_ID`, но `bronivik_jr` читает `CRM_API_KEY/CRM_API_EXTRA`, `USERS_SPREADSHEET_ID`, `BOOKINGS_SPREADSHEET_ID`;
- в `docker-compose.yml` выставляются переменные `BOT1_API_KEY/BOT1_API_EXTRA`, но `bronivik_crm` читает `CRM_API_KEY/CRM_API_EXTRA`;
- часть переменных (`DB_PATH`, `API_AUTH_ENABLED`, `API_HTTP_PORT`) не используется YAML-конфигами напрямую.

Следствие:
- новый инстанс легко поднять в неконсистентном состоянии;
- документация и реальная конфигурация расходятся;
- часть изменений в env просто не влияет на поведение.

Что сделать:
- привести все env-имена к одному контракту;
- удалить мёртвые переменные;
- завести smoke-test загрузки конфигурации в CI.

### 9. Failover для пользовательских состояний создаёт split-brain и не соблюдает TTL в memory fallback

Где:
- `bronivik_jr/internal/repository/failover.go:14-99`
- `bronivik_jr/internal/repository/memory.go:11-67`
- `bronivik_jr/internal/bot/bot.go:149-155`

Проблема:
- при сбое Redis состояния пишутся в память, но после восстановления не переносятся обратно;
- `ttl` в `MemoryStateRepository` вообще не используется;
- лимиты в памяти хранятся на указателях без отдельной синхронизации на запись.

Следствие:
- после краткого сбоя Redis пользователи и rate limit живут в двух разных хранилищах;
- старые диалоги могут "висеть" бесконечно;
- логика ограничений перестаёт быть детерминированной.

Что сделать:
- реализовать TTL cleanup в memory fallback;
- при recovery синхронизировать состояние обратно в primary;
- сделать rate-limit entry потокобезопасным.

### 10. В `bronivik_crm` менеджер получает успешный ответ даже если обновление статуса не сохранилось в БД

Где:
- `bronivik_crm/internal/bot/bot.go:551-570`

Проблема:
- ошибки `UpdateHourlyBookingStatus()` игнорируются через `_ =`.
- После этого бот всё равно отправляет "Бронирование подтверждено/отклонено" и шлёт уведомления пользователю.

Следствие:
- пользователь и менеджер могут увидеть статус, которого в БД нет;
- при проблемах с БД будет ложное подтверждение действий.

Что сделать:
- обрабатывать ошибку и прекращать сценарий;
- логировать booking id и не отправлять уведомления до успешного коммита.

### 11. Часть ошибок конфигурационной синхронизации и обновления профиля тихо игнорируется

Где:
- `bronivik_crm/internal/db/config_sync.go:71-79`
- `bronivik_crm/internal/db/database.go:88-104`

Проблема:
- создание holiday overrides игнорирует ошибки `SetDayOff`;
- `GetOrCreateUserByTelegramID()` игнорирует ошибки `UPDATE users ...`.

Следствие:
- конфиг может быть применён не полностью без явного сигнала;
- профиль пользователя в БД может остаться устаревшим, а сервис вернёт "успех".

Что сделать:
- убрать best-effort без отчёта;
- собирать и возвращать частичные ошибки;
- добавить structured logs на каждый пропуск.

### 12. `/api/items/availability` в `bronivik_jr` делает N * D запросов к БД и плохо масштабируется

Где:
- `bronivik_jr/internal/api/availability_api.go:76-100`
- `bronivik_jr/internal/api/availability_api.go:157-192`

Проблема:
- для каждого аппарата и для каждой даты вызывается отдельный `GetItemAvailabilityByName()`.
- На диапазоне 90 дней и десятках аппаратов это превращается в тысячи SQL-запросов на один HTTP call.

Следствие:
- endpoint будет деградировать по latency и давить БД под отчётной нагрузкой;
- при росте количества аппаратов/дней это станет bottleneck.

Что сделать:
- собирать availability батчами по item_id/date;
- использовать уже существующий `GetAvailabilityForPeriod()` или SQL с `GROUP BY`;
- кешировать ответ на короткое время для read-heavy сценариев.

## Low / Architecture

### 13. `bronivik_jr` Google Sheets service запускает фоновые goroutine без механизма остановки

Где:
- `bronivik_jr/internal/google/sheets_simple.go:28-77`

Проблема:
- `WarmUpCache` и периодический refresh живут на `context.Background()` и не останавливаются вместе с сервисом.

Следствие:
- лишние goroutine в долгоживущих тестах и при повторной инициализации;
- хуже контролируется shutdown.

Что сделать:
- передавать родительский `context.Context` в конструктор;
- завершать фоновые циклы на shutdown.

### 14. В `bronivik_crm` есть дублирующиеся и, похоже, неиспользуемые реализации booking/schedule-логики

Примеры:
- `bronivik_crm/internal/booking/*`
- `bronivik_crm/internal/slots/generator.go`
- `bronivik_crm/internal/manager/service.go`

Проблема:
- в рантайме бот использует один код-путь, а рядом лежит другой, со своей логикой длительности, обеденного перерыва и статусов;
- это уже привело к дрейфу правил между UI, DB и альтернативными пакетами.

Следствие:
- поддержка и ревью дорожают;
- баги фиксируются в одном месте, но остаются в другом.

Что сделать:
- удалить мёртвый код или реально подключить его как единственный source of truth;
- не держать две конкурирующие реализации FSM/slots одновременно.

### 15. CI/CD и workflow-слой нуждаются в чистке и выравнивании

Где:
- `.github/workflows/ci.yml:18-20`
- `.github/workflows/ci.yml:46-57`
- `.github/workflows/ci.yml:70-90`
- `.github/workflows/ci.yml:124-130`
- `bronivik_jr/.github/workflows/ci.yml`

Проблема:
- root workflow использует `Go 1.22` для `bronivik_crm`, хотя модуль объявлен на `1.24`;
- есть дублирующий workflow внутри `bronivik_jr`;
- линтерный action устаревший и не проверялся локально.

Следствие:
- CI становится недетерминированным и зависит от неявной загрузки toolchain;
- часть сигналов дублируется, часть может расходиться.

Что сделать:
- синхронизировать Go version с `go.mod`;
- оставить один authoritative workflow;
- зафиксировать версию `golangci-lint` и добавить локальную цель в Makefile/CI bootstrap.

## Отдельные наблюдения и оптимизации

- `bronivik_jr/internal/bot/middleware.go:20-31`: `trackActivity()` создаёт отдельную goroutine на каждый update. На большом потоке это лишняя нагрузка на scheduler и БД. Лучше батчить или обновлять activity не чаще заданного интервала.
- `bronivik_jr/internal/events/events.go:61-74` и `bronivik_jr/cmd/bot/main.go:318-360`: event bus и обработчики глотают ошибки после логирования. Для синхронизации с Google Sheets это означает silent data loss при сбоях подписчиков.
- `bronivik_jr/internal/config/config.go:154-180`: жёсткая зависимость от `.env` ломает env-only deployment. Нужно сначала читать реальные env vars и только опционально подмешивать `.env`.
- `bronivik_jr/internal/database/bookings.go:68-103` и `bronivik_crm/internal/db/database.go:1111-1155`: текущая защита от гонок опирается на транзакцию без явных row/exclusion locks. Для SQLite это ещё терпимо, для PostgreSQL нужно отдельное конкурентное ограничение на уровне БД.

## Рекомендуемый порядок исправлений

1. Исправить переполнение слотов в `CreateExternalBooking()` и унифицировать статусную модель между сервисами.
2. Починить multi-slot бронирование в `bronivik_crm`.
3. Развести `worker mode` и `bot mode` в `bronivik_jr`.
4. Привести PostgreSQL-ветку к рабочему состоянию или явно снять её из поддерживаемых сценариев до исправления.
5. Убрать drift конфигов/`.env.example`/Compose.
6. Вынести расчёт слотов в один общий модуль и закрыть тестами обеденный перерыв, overrides и диапазоны.
7. После этого уже делать производительные улучшения (`/api/items/availability`, activity batching, shutdown фоновых goroutine).
